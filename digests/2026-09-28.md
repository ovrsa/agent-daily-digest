## Must Read

### 1. [cargo-mutants でテストの穴を測って、proptest と kani で埋める (追記 miri)](https://zenn.dev/mizchi/articles/rust-mutants-proptest-kani)

ソース: mizchi / 公開: 2026-09-25

**何をしたか／何が分かったか**

著者は、AIに試させた Rust のミュータントテストを整理し、cargo-mutants で73件中23件が生存、ring.rs の kill 率が71%（45/63）で行カバレッジ79.7%を下回ったと報告している。

**読む理由**

AIが書いたテストを行カバレッジだけで信用せず、mutation kill 率と参照モデル型のテストで穴を測る手順が具体的に分かる。

**根拠**

VecDeque を参照モデルにした proptest 1本で、ring.rs の生存 mutant が18件から0件（63/63、0.09秒）になった。miri は256ケースでネイティブ0.04秒に対し277秒かかった。

**留保**

著者は kani の理解がまだ浅く、誤記が残る可能性を述べている。多項式剰余の kani 検証は10分で終わらず、Lean での証明案も試されていない。

### 2. [Human-AI partnerships are for alignment, not capability](https://www.seangoedecke.com/human-ai-partnerships-are-for-alignment-not-capability/)

ソース: goedecke / 公開: 2026-09-27

**何をしたか／何が分かったか**

著者は、エージェントが書くコードは間違いが少なく速い一方、仕事で完全なバイブコーディングをすると保守性や長期戦略との不整合で出力がひどくなると述べ、人間の役割は組織の価値観への整合だと主張している。

**読む理由**

プロンプトにタスクだけでなく優先事項の文脈を入れる助言と書き方の例が得られ、自分の指示文の見直しに使える。

**根拠**

著者は、バグ回避・可観測性・既存コードへの馴染み・性能の相対的な優先度を段落で書き、下げてよい項目も明示すると述べる。個人プロジェクトではプロンプトの約半分が文脈で、明示仕様だけなら見落とした改善があったとする。

**留保**

測定や比較はなく、個人の観察と一例に基づく。モデルの挙動をRL採点器のせいとする説明は、本文で「presumably」と留保されている。

**留保**

実際のセッション結果や測定値は示されていない。取得した資料では、Codexの /goal edit とゴール文4,000文字上限は裏付けられていない。

### 4. [Codexを使うなら、codex execと構造化出力を押さえておきたい](https://syu-m-5151.hatenablog.com/entry/2026/09/26/103930)

ソース: syu-m-5151 / 公開: 2026-09-26

**何をしたか／何が分かったか**

著者は、codex exec の --json は実行イベントのJSONL出力で、最終回答の形は --output-schema、最後の回答の保存は -o で扱うと整理し、Claude Code では structured_output から取り出すと述べている。

**読む理由**

CIやスクリプトからエージェントを呼ぶとき、成功・失敗・未確認をどう区別して受け取るかの設計を、公式文書と照らして確認できる。

**根拠**

著者は、ネットワークや認証の失敗を空の findings に変換すると「懸念なし」と区別できなくなると指摘する。実行ごとに mktemp -d で保存先を作る例を示し、前回の結果が残ると古いJSONを後続処理へ渡しうるとする。

**留保**

例のjqは主要項目の型を見る簡易検査で、Schema全体の検証ではない。条件を保存してもモデルの回答は完全には再現しないと本文が述べている。

### 5. [Codexを使うなら、定期タスクを押さえておきたい](https://syu-m-5151.hatenablog.com/entry/2026/09/25/102941)

ソース: syu-m-5151 / 公開: 2026-09-25

**何をしたか／何が分かったか**

著者は、Codexのローカル定期タスクはPC起動とデスクトップアプリの稼働が必要で、毎回新しい会話で始まるため前提を依頼文に含めるべきだと述べている。

**読む理由**

定期実行を設定する前に、実行場所、承認、取得失敗の報告方法を点検する項目として使える。

**根拠**

著者の依頼例は「直近24時間のコミットを確認」し、確認できなかった範囲を残す指示を含む。24時間基準では休日やマシン停止で数日空くと漏れると述べる。Claude Code Desktopは復帰時に7日以内の逃した実行を1回だけ追い付き実行する。

**留保**

著者は公式資料に基づいて説明しており、自分で定期実行を走らせた結果は示していない。確認済み位置の更新順序は製品機能ではなく運用方針だとする。

**読む理由**

**留保**

Digital Twinの作り方は著者の理解に基づく伝聞。著者は、StrongDM方式が1エンジニア月2万ドルなら関心は下がると述べる。豪州サイトの件と訓練の関連は推測にとどまる。

### 7. [Kākāpō Party](https://simonwillison.net/2026/Sep/26/kakapo-party/)

ソース: simonw / 著者: Simon Willison / 公開: 2026-09-26

**何をしたか／何が分かったか**

著者は、生成したHTML canvasアニメをローカルのClaude Codeに渡し、ブラウザで開いてクリックする15秒の動画を作るよう指示し、Claude CodeがPlaywrightで動画を生成した。

**読む理由**

操作した状態の動画を、時刻とクリック位置を自然言語で指定して作らせる具体例で、デモ動画作りに応用できる。

**根拠**

Claude Codeのスクリプトは 1280x720 で record_video_dir を指定して録画し、3.0秒から13.2秒の間に10回クリックして16.0秒まで待つ。著者の指示には「don't start clicking until 3s in」がある。

**留保**

1回の事例で、出来は著者の主観評価。指示は15秒だがスクリプトは16.0秒まで待ち、完成した動画の長さは本文に書かれていない。

### 8. [You should all be asking way more questions](https://www.seangoedecke.com/you-should-all-be-asking-way-more-questions/)

ソース: goedecke / 公開: 2026-09-25

**何をしたか／何が分かったか**

著者は、AIエージェントに「このコードベースの別の場所でも同じことをしているか」「なぜこのファイルを触る必要があるのか」といった質問を日常的に投げると述べている。

**読む理由**

実装後のレビューに頼らず、設計上の疑問を質問で当てる習慣を、自分の出力検証に取り入れるか判断できる。

**根拠**

著者は、質問の約半数でモデルが誤りを犯したと確信できる回答が返ると述べる。人間の説明でも平均30秒に1回質問し、早い段階の小さな誤解が後で大きくなるのを防ぐとする。

**留保**

約半数という数値は著者の主観的な経験で、測定方法や試行数は示されていない。誘導的な質問による迎合の検証もない。

### 9. [Bluesky reply bot checker](https://simonwillison.net/2026/Sep/27/bluesky-bot-check/)

ソース: simonw / 著者: Simon Willison / 公開: 2026-09-27

**何をしたか／何が分かったか**

著者は、Opus 5.5にバイブコーディングさせ、Blueskyのプロフィールに返信ボットの兆候があるかを調べるツールを作り、判定の根拠を示すことをプロンプトで求めた。

**読む理由**

「判断の過程を見せる」要件を最初に指定し、見逃し事例からシグナルを足す反復の実例として、単機能ツールをエージェントに作らせる進め方を確認できる。

**根拠**

最初のコミットは最大1,000件の投稿を走査し、各シグナルに測定値・ルール・理由・無害な説明を示す。返信が遅い自動アカウントが「兆候少」と採点された事例を受け、「Never replies back」などのシグナルを加えた。

**留保**

精度や誤検出率の測定はなく、閾値や実装コードも取得できていない。プルリクエストは4件のチェックのうち1件のみ通過した状態でマージされている。
